# Info History

필요한 과거 판단을 찾아 읽는 기록이다. 현재 책임은 [개발 README](README.md), 동작의 약속은 [계약](contract.md), 기록 방법은 [History 기록 기준](../README.md#history-기록-기준)을 따른다. 기록 날짜는 기록일이며, 이전 개발을 정리한 항목은 실제 결정일과 다를 수 있다.

## 2026-10-09 · 대지 지정의 형상 범위

Contour의 선택 대지는 경계선 대신 곡면 상면을 가진 입체가 정보의 원본이다. 같은 객체 기반 정보 계약을 유지하기 위해 대지 지정을 유효한 닫힌 Curve뿐 아니라 닫힌 Brep·Extrusion에 허용했다. 별도 경계 객체나 대지 원장을 추가하지 않는다. 형상 편집으로 입체가 열려도 기존 정보를 찾고 지정을 해제할 수 있도록 읽기는 저장된 flag를 유지하고, 쓰기는 현재 형상을 검사한다. [계약](contract.md#부분-수정과-보존), [형상별 지정·Undo 검사](../../src/info/checks/native/InfoNativeChecks.cs).

## 2026-10-09 · 잘못된 업무 필드의 수정 진입점 보존

루트 형식이 유효하면 잘못된 업무 필드도 읽어 고칠 수 있지만, 고급 JSON 편집을 열기 전에 전체 필드를 검증하면서 잘못된 `parcels` 등의 복구를 막고 있었다. 편집창 진입에서는 입력과 루트 형식을 확인하고, 변경 적용·저장 시 공통 검증으로 전체 결과를 확인하도록 구분했다. 기존 정보를 자동 보정하거나 저장 검증을 완화하지 않는다. [계약](contract.md#대상과-충돌), [복구·미확정 입력 보존 검사](../../src/info/checks/native/InfoPanelChecks.cs).

## 2026-10-05 · 패널에서 숫자를 반올림한 뒤 검증하던 경계 수정

공통 Info 검증은 층수의 소수 부분과 표현 범위보다 작은 수치를 원 JSON 토큰으로 검사했지만, 패널의 기본 수치 입력은 먼저 `double`로 바꾸고 있었다. 이 때문에 큰 소수 층수는 정수가 되고 아주 작은 수치는 0이 되어 MCP와 다른 검증 결과를 낼 수 있었다. 다른 항목만 수정해도 기존의 큰 정수나 정밀한 소수가 바뀔 수 있는 같은 원인이었다.

입력 단계의 변환이 업무 검증보다 먼저 의미를 바꾸지 않도록 패널도 숫자 토큰을 보존한 채 공통 검증을 사용하게 했다. 같은 원인이 있는 추가 숫자 입력까지 이 경계를 맞추고, 편집하지 않은 값은 재작성하지 않도록 했다. 현재 수치·미입력 보존 규칙은 [계약](contract.md#대상과-충돌), 반올림·underflow·기존 정밀도 손실의 재현은 [InfoPanelChecks](../../src/info/checks/native/InfoPanelChecks.cs)에 있다.

## 2026-10-05 · 외부 문서 연결 대신 객체 속성을 원본으로 선택

처음에는 모델과 연결된 Markdown·YAML 문서에 대지 정보를 보관하는 방식을 검토했다. 그러나 한 문서에 여러 대지가 있거나 객체를 복사·Import할 때 별도 파일, 대지 ID, 그룹 원장을 유지하면 연결 오류와 동기화 책임이 늘어난다. Rhino 객체의 ObjectAttributes User Text에 `aha.info` JSON을 저장하고 그 객체를 정보의 원본으로 삼았다. 복사된 객체의 정보도 독립적으로 유지한다.

이 선택으로 Rhino의 저장·복사·Undo 경로를 활용할 수 있었다. 객체 정보의 저장·재열기·Import와 복사 후 독립 수정은 [InfoNativeChecks](../../src/info/checks/native/InfoNativeChecks.cs)에 재현했다. 외부 자료 교환이 필요해지더라도 객체의 원본과 교환 기능의 책임을 다시 구분해야 한다는 판단을 남긴다.

## 2026-10-05 · Site 전용 도구에서 출처에 독립적인 Info로 범위 변경

대지 법규를 채우는 Site 도구를 먼저 생각했지만, 같은 저장 방식을 건물·도로·임의 객체에도 쓸 수 있도록 Info의 책임을 속성 CRUD로 좁혔다. 자료 취득은 Topo·EumCrawl 같은 도구가 맡고, Info는 그 결과와 사용자 입력을 같은 규칙으로 다룬다. 취득 출처별 설명과 법규 판정을 Info에 넣는 방향은 채택하지 않았다.

`kind`는 Rhino 형상 타입과 별개의 의미상 분류로 정했다. 또한 필지 면적은 기하 면적과 다를 수 있고 미입력은 0이나 제한 없음이 아니므로, 이 차이를 데이터 형식에서 보존했다. 앞으로 다른 도구가 기록한 항목을 잃지 않도록 확장 정보를 보존하는 판단도 함께 유지했다. 관련 경계는 [InfoData](../../src/info/shared/InfoData.cs)와 [정보 계약 검사](../../src/info/checks/Program.cs)에 담겨 있다.

## 2026-10-05 · 선택 변경과 편집 충돌에서 저장 대상을 고정

패널 편집 중 선택 객체가 바뀌거나 다른 도구가 정보를 수정할 수 있어, 저장 시점의 선택을 다시 따라가면 다른 대상을 덮어쓰거나 최신 정보를 잃을 수 있었다. 편집을 시작한 대상을 고정하고 원본 변경 여부를 확인하도록 했다. 현재 저장·보존 규칙은 [계약](contract.md#대상과-충돌)에 둔다.

선택 변경, 미확정 필지 편집, 외부 수정, 부모 레이어 잠금은 [InfoPanelChecks](../../src/info/checks/native/InfoPanelChecks.cs)에 재현했다. 패널과 MCP가 같은 [InfoService](../../src/info/rhino/InfoService.cs)를 사용하게 한 이유는 이 보호가 진입 방식에 따라 달라지지 않도록 하기 위해서다.
