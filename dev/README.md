# AHA 개발 안내

현재 코드를 이어받기 위한 문서다. [Ground Rule](Ground_Rule.md) → [개발 인덱스](index.md) → 작업 대상의 README → 계약 순으로 읽고, 변경에 필요한 설계·연결된 계약·검사 안내를 찾는다. [환경·빌드·전체 검사](aha/build-and-test.md)는 AHA 공통 기반에서 관리한다. 사용자 안내는 [제품 README](../README.md)와 [docs](../docs/index.md)에 있다.

## 소유권과 구조

`aha`, `topo`, `info`, `eum-crawl`, `setting`은 `src/`, `dev/`, `docs/`에서 같은 이름과 위계를 사용한다. `aha`는 플러그인·MCP·패널·문서 관리·패키징 등의 공통 기반이며, 나머지는 독립적으로 사용하는 도구다. 일대일 대응은 이 **책임 단위**에 적용한다. 내부 파일과 하위 폴더까지 기계적으로 복제하지 않는다.

```text
src/<소유자>/             구현과 checks/
dev/<소유자>/README.md    목적·책임·문서 안내·소스와 검사 진입점
dev/<소유자>/contract.md  입력·결과·변경과 보존·실패 처리·의존 계약
dev/<소유자>/...          필요한 설계·주제별 문서
dev/<소유자>/HISTORY.md   필요한 경우 찾아 읽는 결정·발견·비교 기록
docs/<소유자>/README.md   사용자가 알아야 할 기능·사용법·한계
dev/references/           외부 자료별 설명과 참고 파일
```

모든 소유자는 README와 계약을 둔다. README는 목적·전략·책임을 설명하고, 어떤 작업에서 어떤 문서를 읽을지 안내한다. 내부 구성과 처리 흐름을 독립적으로 설명할 필요가 있으면 `architecture.md`를 두며, 별도 주제가 커지면 목적이 분명한 문서로 나눠 README에서 연결한다. 짧은 소스 역할 설명은 README에 둘 수 있다. 같은 문서 수·세부 목차를 강제하거나 내용 없는 파일을 만들지 않는다. 다른 방식의 구현이나 내부 모듈이 늘어나도 상위 도구의 소유권을 유지한다.

## 문서 관리

| 내용 | 원본 위치 |
|---|---|
| 도구 조합과 독립 개발의 대원칙 | [Ground Rule](Ground_Rule.md) |
| 작업 시작·수정·인계 규칙 | [AGENTS.md](../AGENTS.md) |
| 목적·책임·개발 관점·문서와 구현 진입점 | 해당 `dev/<소유자>/README.md` |
| 외부에서 의존할 입력·결과·동작의 약속 | 해당 `dev/<소유자>/contract.md` |
| 현재 구성·처리 흐름·주요 설계 이유 | 해당 소유자의 `architecture.md` 등 설계 문서 |
| MCP 통신·등록과 업무 호출의 연결 | [공통 MCP 안내](aha/mcp.md), 업무 의미는 각 소유자의 계약 |
| 환경·빌드·설치·전체 검사 | [빌드·검사 안내](aha/build-and-test.md), 세부 검사는 소유자별 `checks/README.md` |
| 설치·사용법·입출력 의미·사용자가 알아야 할 제약 | 해당 `docs/<소유자>/` |
| 과거 결정·폐기 이유·중요한 발견·재검토 후보 | 해당 `dev/<소유자>/HISTORY.md` |
| 외부 구현·공식 문서·연구·참고 파일 | [references](references/README.md) |
| 현재 동작을 판정하는 재현 입력·검사 | 해당 `src/<소유자>/checks/` |

작업 시작 시 영향받는 소유자를 정하고 그 범위의 구현·검사·문서를 함께 수정한다. 여러 도구에 걸친 규칙은 책임지는 소유자 한 곳에 설명하고 다른 곳에서는 필요한 절을 연결한다. 공통 기반 변경은 `aha`에서 다룬다. 개발 인덱스는 책임·연결·계약 링크를 제공하며 상세 필드나 오류 규칙을 복제하지 않는다.

현재 지침·상세 계약은 한 곳에서 관리하고 다른 문서는 요약과 링크로 연결한다. 사용자 문서에는 개발 지시나 과거 논의를 넣지 않는다. 현행 문서는 독자가 개발 대화를 몰라도 이해할 수 있도록 현재 책임·계약·설계를 설명한다. 작성 과정·임시 진행 상황·AHA 개발의 종료를 전제하는 명칭을 넣지 않는다. 작업·검사의 완료 상태와 개발 자체의 종료는 구분한다. History만 고쳐 현재 계약 변경을 대신하지 않는다.

### 계약 문서

계약은 도구의 내부를 몰라도 안전하게 사용할 수 있는 약속이다. 공개 실행 기능과 지속되는 정보 형식을 다루며 모든 내부 함수의 서명을 나열하지 않는다. 다음 내용을 필요한 만큼 담는다.

| 내용 | 기록할 사항 |
|---|---|
| 책임과 제공 기능 | 기능별 진입 경로, 조회·변경 여부 |
| 입력과 결과 | 필수값·기본값·단위·미입력 의미·결과 형식 |
| 변경과 보존 | 대상·부작용·정보 보존·실패·취소·충돌 처리 |
| 의존 계약 | 다른 도구·저장 형식·외부 서비스에 전달하는 입력과 기대 결과, 실패 시 동작 |
| 구현과 검사 연결 | 실제 서비스·스키마·약속을 보호하는 핵심 검사 |

목차와 예시는 내용에 맞게 정한다. 공통 정보 형식은 [Info 계약](info/contract.md)을 연결하고, 각 도구는 자신이 기록하거나 사용하는 항목의 의미만 설명한다. 서비스 호출과 정보 형식 공유를 구분한다. 외부 서비스의 보장과 AHA의 기대·검증 조건도 구분하며 관측한 응답을 공급원의 영구 보장으로 쓰지 않는다.

계약은 기대 동작, 설계 문서는 그 동작을 구현하는 구성과 선택 이유, 검사는 그 약속의 자동 판정을 설명한다. 실제 스키마 전체를 Markdown에 복제하지 않고 코드로 연결하되 단위·미입력·보존 등 스키마만으로 알 수 없는 의미는 계약에 적는다. MCP 클라이언트에 필요한 설명은 실제 도구 등록에도 반영한다. 문서와 구현이 다르면 원인을 확인하며 현재 코드의 우연한 동작을 약속으로 고정하지 않는다.

### 계약 변경

1. 바꾸려는 약속의 소유자를 정하고 [개발 인덱스](index.md)와 계약 간 링크에서 호출자·정보 소비자·외부 의존성을 확인한다. 변경한 파일 경로·명령·필드명을 참조하는 문서와 검사도 검색해 연결을 확인한다.
2. 입력·출력·저장 형식·부작용 중 무엇이 달라지는지 확인한다. 다른 도구의 내부 수정 없이 사용할 수 있는 경계를 유지하고, 기존 소비자에 영향이 있으면 함께 변경 범위에 포함한다.
3. 같은 변경에서 구현·관련 핵심 검사·계약을 갱신한다. MCP 경로에 영향이 있으면 도구 설명·스키마·호출 변환·응답도 대조한다. 검사 등록이 바뀌면 `checks/suites.json`도 갱신한다.
4. 설계가 달라지면 설계 문서를, 역할·연결이 달라지면 개발 인덱스를, 사용자 동작이 달라지면 제품 문서를 갱신한다. 공개 도구 목록이 달라지는 경우 사용자 인덱스도 확인한다.
5. 관련 검사를 실행하고 링크·명령·형식 설명을 확인한다. 문서만 바꾸었다면 링크·앵커·구현 및 검사 연결을 확인하며 제품 검사를 불필요하게 반복하지 않는다. 과거 판단은 아래 History 기준으로 보존 가치를 판단한다.

큰 변경에 실행 계획이 필요하면 해당 소유자 아래 `plan.md` 등으로 목표·범위·진행 방법·검증 조건을 관리할 수 있다. 계획을 현재 구현의 설명으로 사용하지 않는다. 구현에 반영한 계약과 설계는 현행 문서에 갱신하고, 더 이상 실행하지 않는 계획은 선택적 기록으로 남길 이유를 판단한다.

## History 기록 기준

History는 **향후 판단에 필요한 결정·발견·비교를 선별 관리하는 기록**이다. 현재 계약·설계만으로 판단하기 어렵거나, 같은 문제가 재발하거나, 폐기한 방식을 재검토할 때 관련 제목으로 필요한 부분을 찾아 읽는다. 현행 지침이나 실행 장부로 사용하지 않는다.

중요한 선택이나 작업 정리 시 별도 요청 없이 보존 가치를 판단한다. 다음 내용을 빠뜨리면 조사·실수·잘못된 접근을 반복할 수 있는지가 기준이다.

- 책임·계약·저장·연결 등의 선택, 비교·폐기한 대안과 그 이유.
- 중요한 오류의 근본 원인과 재현 검사, 결과의 해석에 영향을 주는 한계.
- 아직 채택하지 않은 유용한 생각과 **다시 검토할 조건**. 확정 지침이나 구현 약속으로 적지 않는다.

관련 기존 기록을 먼저 확인해 보충·병합·축약하고, 고유한 보존 가치가 사라진 내용은 삭제한다. 과거와 현재의 선택을 비교할 가치가 있으면 대체한 이유를 함께 남긴다. 오래됐다는 이유로 폐기 근거를 지우거나 당시 사실을 현재 결정처럼 바꾸어 쓰지 않는다. 이동·병합 시 연결된 링크도 갱신한다.

매 작업마다 기록하거나 미기록 사유를 남길 필요는 없다. 대화·실행 순서·임시 상태·통과 개수·원시 로그·비밀정보는 제외하고, 현행 문서·검사를 복제하지 않고 연결한다. 근거 없는 과거 이유·수치·날짜는 추측하지 않는다.

### 작성 형식

소유자별 `HISTORY.md`에 `## YYYY-MM-DD · 주제`로 기록일과 주제를 적고 문제·선택·이유를 보통 1~3개 문단으로 쓴다. 근거가 되는 코드·검사·자료를 연결하고, 결과의 한계나 미채택 안의 재검토 조건은 필요할 때만 덧붙인다. 신규 기록은 위에 두되 같은 주제는 기존 기록에 통합할 수 있다.

날짜는 기록일이다. 과거 내용을 병합할 때는 판단의 시점을 왜곡하지 않도록 기존 날짜를 보존하거나 병기한다. 실제 결정일을 모르면 추측하지 않는다. 분량 때문에 나눌 때는 같은 소유자 안에 두고 HISTORY에서 연결한다.

작성 기준은 OpenAI의 [문서화 참고 내용](references/OpenAI/README.md)을 AHA에 맞게 적용한 것이다. 이 파일명과 구조는 AHA의 선택이며 Codex의 필수 형식이 아니다.
